# Подтверждение реконструкций

Под тегом `#stub` (и `#inferred`) прячутся **две независимые вещи**, и путать их дорого:

| | вопрос | где живёт | когда меняется |
|---|---|---|---|
| **происхождение** | откуда мы это знаем | тег `#stub` / `#inferred` | когда меняется источник |
| **подтверждение** | сверял ли это человек, когда и по чему | журнал `model/verified.json` | при каждой сверке |

Подтверждение **не снимает тег**. Оно сбрасывает таймер.

## Почему тег не снимается

Если снять `#stub` после первой сверки, теряется факт «это наша реконструкция чужой системы». Через полгода она снова разъедется с реальностью, но метки уже нет, и все считают её фактом. Реконструкция остаётся реконструкцией — меняется только то, насколько свежо мы её проверяли.

**Тег снимается, только когда меняется источник знания:**

- соседняя команда завела свою модель → `#stub` уходит, появляется `import` (см. `CONTRACTS.md`);
- сервис перешёл к нам → это больше не чужая система;
- контракт стал генерироваться из кода вместо ручного описания → `#stub` меняется на `#inferred`.

Все три — события, а не решения одного человека.

## Чем подтверждали — важнее, чем факт подтверждения

Срок годности зависит от силы основания:

| `--against` | что это значит | срок |
|---|---|---|
| `docs` | прочитали чужую документацию | 90 дней |
| `owner` | владелец системы подтвердил письменно или в PR | 180 дней |
| `probe` | сверено с реальностью: трафик, OpenAPI с прода, контрактный тест | 365 дней |

Подтверждение по документации — самое слабое: чужая дока врёт примерно так же часто, как наша модель. Для боевых путей линтер отдельно предупреждает, что `docs` мало и нужен `probe`.

## Подтверждение привязано к состоянию, а не к элементу

Это главная механика. При подтверждении считается **hash наблюдаемой поверхности**: все утверждения об элементе и его потомках — типы, метаданные, связи, названия. Как только что-то из этого меняется, подтверждение автоматически перестаёт действовать:

```
$ npm run gen         # анализатор нашёл новый query-параметр
$ npm run check
WARN  shop.orders.api  поверхность изменилась после подтверждения (2026-08-17, a.petrov) — переподтвердить
```

Без этого подтверждение превращается в галочку: человек один раз сверил, потом модель десять раз поменялась, а «проверено» так и висит.

Поверхность считается **вместе с потомками**, поэтому подтверждают корень реконструкции, а не каждый эндпоинт: сверил API целиком — покрыты все его операции.

## Как это выглядит

```bash
# подтвердить
node tools/verify.mjs build/model.json shop.orders.api --by=a.petrov --against=probe \
  --note='сверено с OpenAPI с прода'

# посмотреть журнал
node tools/verify.mjs build/model.json --list
2026-08-17  sms                               docs   a.petrov    актуально
2026-08-17  shop.orders.api                   probe  a.petrov    актуально
2026-08-17  shop.orderCreated.ordercreatedv1  owner  i.smirnov   актуально
```

Журнал — `model/verified.json`, append-only. История пересмотров видна: кто, когда, по чему и что при этом было в модели.

## Что проверяет линтер

Всё — предупреждения, не ошибки: непроверенная реконструкция мешает, но не должна блокировать поставку.

- реконструкция без единого подтверждения;
- поверхность изменилась после подтверждения → переподтвердить;
- подтверждение протухло по сроку своего типа;
- `#stub` на боевом пути подтверждён только `docs` → нужен `probe`;
- низкий `confidence` у извлечённого эндпоинта — но **только если его никто не смотрел**: подтверждение родительского API снимает это предупреждение.

## Почему журнал, а не поле в `.c4`

1. `.gen.c4` перезаписывается генератором — любая ручная правка там будет затёрта.
2. Подтверждение — это событие (кто, когда, по чему), а не свойство элемента.
3. Журнал даёт историю: видно, что систему пересматривали трижды и каждый раз находили расхождения — это сам по себе сигнал.
