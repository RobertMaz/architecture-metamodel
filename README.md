# Архитектурная модель

Модель ландшафта как код. Живёт в git, проверяется в CI, рендерится на сайт.

```bash
npm install
npm run dev      # http://localhost:5173
npm run check    # то же, что в CI
```

**Начни с [CHEATSHEET.md](CHEATSHEET.md)** — одна страница, больше знать не надо.
**Контрактный слой (API, эндпоинты, схемы) — в [CONTRACTS.md](CONTRACTS.md).**
**Подтверждение реконструкций — в [VERIFICATION.md](VERIFICATION.md).**
**Свои / соседние / внешние системы — в [TIERS.md](TIERS.md).**

## Что здесь

```
model/
  00-spec.c4        типы элементов, типы связей, теги
  10-shop.c4        файл на систему, владелец — команда (см. CODEOWNERS)
  20-views.c4       виды: по одному на реальный вопрос
  verified.json     журнал: кто, когда и по чему сверял реконструкции
  gen/*.gen.c4      контрактный слой, генерируется, руками не править
tools/
  check.mjs         инварианты метамодели, роняют CI
  gen-api.mjs       api-source/*.json -> model/gen/*.gen.c4
  owners.mjs        владелец системы из CODEOWNERS
  api-source/       выход анализатора кода, источник правды по контрактам
  impact.mjs        кто сломается, если поменять X
  verify.mjs        журнал подтверждений + hash поверхности
  drift.mjs         сверка модели с тем, что реально крутится
  live-services.txt выгрузка из кластера, обновляется скриптом
.github/workflows/
  architecture.yml  check + drift + картинки в PR + публикация сайта
```

## Зачем это, если есть Confluence

Метамодель — не то, что убивает такие проекты. Убивают четыре вещи, и вот ответ на каждую:

| проблема | что здесь сделано |
|---|---|
| стоимость изменения выше пользы | сервис добавляется десятью строками; всё, что дороже, из модели выкинуто |
| у модели нет потребителя | владельцы, репозитории и рунбуки берутся отсюда; impact-анализ — отсюда же |
| один автор на всю компанию | файл на систему + CODEOWNERS, ревьюит команда-владелец |
| нет момента, когда обновление обязательно | `check` блокирует PR, `drift` находит незадокументированное |

## Инварианты (tools/check.mjs)

Ошибки роняют сборку:

- у каждой системы есть владелец в CODEOWNERS, и он не продублирован в модели;
- клиент не может быть целью связи;
- воркер не принимает `call`;
- `store` ничего не инициирует, в него ведут только `read`/`write`;
- в канал ведёт только `publish`, из канала — только `deliver`;
- **у хранилища ровно один писатель** — детект shared database;
- границу системы пересекают только элементы с `#public`;
- если у контейнера описан контракт — `call` ведёт в конкретный эндпоинт, а не в контейнер;
- нельзя звонить в эндпоинт с прошедшим `sunset`;
- нет дублей `method + path` внутри одного API;
- внешняя система не описана изнутри, у неё есть договор;
- у соседей описано только то, чем мы пользуемся;
- нет прямого доступа в чужие хранилища.

Предупреждения не роняют: осиротевшие элементы, отсутствие ссылки на репозиторий, хранилища без писателей, непроверенные и протухшие реконструкции (см. [VERIFICATION.md](VERIFICATION.md)).

Проверено на живых нарушениях:

```
ERROR shop.gw -[call]-> shop.notifier      у воркера нет публичного API
ERROR shop.orders -[call]-> shop.orderCreated  в канал ведёт только publish
ERROR shop.billingDb   пишут несколько сервисов (billing, orders) — shared database
```

## Дрейф

Единственная защита от «модель врёт». `tools/live-services.txt` — выгрузка из кластера:

```bash
kubectl get deploy -A -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}' > tools/live-services.txt
node tools/drift.mjs build/model.json tools/live-services.txt
# DRIFT  живёт, но не описано:   loyalty
```

Первые месяцы держи `continue-on-error: true` — сначала модель догоняет реальность, потом проверка становится блокирующей.

## Внедрение

**Неделя 1.** Одна система, только контейнеры, три вида. Показать людям на демо — здесь уже 80% пользы. Ничего не автоматизировать.

**Недели 2–4.** `check` в CI. Остальные команды описывают свои системы (по одному файлу, десять строк на сервис). Дрейф в режиме предупреждений. Сайт публикуется на каждый merge, ссылка — в онбординг.

**Дальше.** Контрактный слой генерацией из кода — см. [CONTRACTS.md](CONTRACTS.md). Начинать с сервисов, у которых больше одного потребителя. Impact-бот в PR: меняешь контракт → комментарий со списком потребителей и команд. Deployment-модель — почти никогда, k8s знает лучше.

Момент обязательности выбери один и держи его: **сервис не считается запущенным, пока его нет в модели.** Строчка в шаблоне сервиса и в чеклисте PR. Без этого не взлетит никакая метамодель, даже идеальная.

## Что решить заранее, а что можно менять потом

Дорого менять: **границы систем** и **идентификаторы**. Id — это ссылки, переименование ломает все виды, где элемент упомянут явно. Title меняй сколько угодно, id — никогда.

Дёшево менять: типы элементов, теги, виды, стили. На них не стоит тратить обсуждение на старте — доспорите в рабочем порядке.

## GitLab

Замени `.github/workflows/architecture.yml` на:

```yaml
architecture:
  image: node:22
  rules:
    - changes: [model/**/*, tools/**/*]
  script:
    - npm ci
    - npm run check
    - npm run build
  artifacts:
    paths: [dist]
```

Владение — через `CODEOWNERS` в корне (синтаксис тот же) плюс `Codeowner approval required` в настройках защиты ветки.
